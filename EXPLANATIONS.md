# Объяснения и проверка качества

Запуск из корня проекта, Python 3.10+; внешние зависимости и API-ключи не нужны:

```powershell
python explanations.py data/profiles.json examples/dataset_request.json
python -m unittest discover -s tests -v
python quality_demo.py
```

`quality_demo.py` проверяет пять фиксированных запросов из
`examples/quality_requests.json` и записывает реальные карточки, сообщения,
счётчики и время выполнения в `data/quality_demo_result.json`.

## Подключение к интерфейсу

```python
from explanations import recommend
result = recommend(profiles, request)
# Показать result["message"], затем result["cards"].
# На каждой карточке показать explanation и notices.
```

Вход совпадает с `select_candidates`: `city`, `category`, `date`, `budget`,
`format`, опционально `language` и `duration_hours`.
Модуль вызывает существующий подбор и сохраняет его порядок и диагностические поля.
Он добавляет:

| Поле | Назначение |
| --- | --- |
| `status` | `matched` — подобрали; `category_absent` — категории нет в городе; `no_matches` — категория есть, никто не проходит |
| `cards` | Имя, категория, город, цена, объяснение, пометки происхождения данных |
| `message` | Понятная сводка, включая причины неполной или пустой выдачи |
| `exclusion_counts` | Взаимоисключающие группы исключённых профилей |
| `quality` | Проверка совпадения объяснений после замены имён |

Сначала определяется каталог города и категории. В нём каждый исключённый профиль
учитывается один раз по приоритету: календарь → бюджет → формат → язык → часы.
Поэтому сумма исключённых и подходящих всегда равна размеру этого каталога.
Все дополнительные причины остаются в исходном `rejected`; непопадание в топ-3
не считается несоответствием условиям. При показе подробных счётчиков интерфейсу
следует также показывать `exclusion_counting`, описывающий порядок подсчёта.

## Точность текста

Объяснение состоит из двух шаблонных предложений: цена относительно бюджета,
затем формат, языки, часы, основание доступности и фрагмент описания.
Фрагмент берётся дословно из профиля; длинные фрагменты обрезаются по границе
слова с многоточием. Это цитата автора профиля, а не независимо проверенная оценка.
Простая эвристика по словам отдаёт предпочтение фрагментам о сценариях,
программах, опыте и услугах, затем фрагментам, отсутствующим у других выбранных подрядчиков.

Цена «от» всегда сопровождается уточнением итоговой стоимости. Отсутствие даты
в `busy_dates` описывается именно как отсутствие отметки о занятости.
`max_hours: null` означает непривязанность работы к часам присутствия.
Синтетические профили, подставленные города и цены получают отдельные пометки.

Если объяснения совпадают даже после удаления имён, `quality` сообщает о недостатке
различающих фактов. Модуль не выдумывает преимущества ради уникальности.
Эта автоматическая проверка выявляет текстовые совпадения; содержательную оценку
близких по смыслу формулировок на новых данных нужно проводить дополнительно.

## Сценарии для защиты

1. `dense`: ведущие Алматы, свадьба 06.10.2026, бюджет 3 млн ₸, русский, 5 ч;
   подходящих больше трёх, виден результат ранжирования.
2. `other_date`: те же условия на 01.10.2026; один из предыдущих выбранных ведущих
   занят, выдача меняется, причина видна в сводке и диагностике.
3. `rare`: флористы Алматы на 04.10.2026, свадьба, бюджет 3 млн ₸;
   только две карточки, поясняется ограниченность каталога.
4. `no_matches`: условия первого сценария с нулевым бюджетом;
   категория есть, результат пустой и объяснён.
5. `category_absent`: флористы в городе/регионе «Зарубежье»;
   в предоставленном каталоге такой категории там нет.

Тесты проверяют факты в карточках, цену «от», происхождение данных, часы `null`,
отсутствующее описание, различия без имён, все причины исключения, отсутствие
двойного счёта, сохранение порядка подбора, перестановку исходных записей,
исключение занятых и смену даты. Ожидаемые ID демо зафиксированы в JSON:
изменение датасета потребует проверки и осознанного обновления ожиданий.
